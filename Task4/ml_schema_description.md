## Общий подход

### Сбор данных

Сбор данных для ML моделей и их дообучения можно разбить на 3 этапа.

1) Этап сбора данных в течение дня, т.е. все изменения через CDC записываются в соотв. топики Kafka ( по топику на сервис);
2) Из топиков Kafka данные будут вычитываться и, при необходимости, трансформироваться и структурироваться Spark Streaming;
3) Далее Spark батчами вставляет данные в ClickHouse (для BI-дашбордов)

### Обработка собранных данных и (до)обучение соответсвующих моделей

Скорее всего ночью, в периоды наименьшей активности сервиса, собранные за день данные надо будет выгрузить
из хранилища(Clickhouse) с помощью Spark, почистить от аномалий  и выбросов, сформировать необходимые датасеты и дообучить существующие модели на новых данных, валидировать модели, после чего задеплоить обновленные модели в соотв. сервисы. Каждый шаг можно описать как узел Dag для Airflow. Таким образом DAG для Airflow будет состоять из следующих шагов:

1) Экспорт и простейшая фильтрация: Spark-скрипт делает запрос в ClickHouse, собирает данные за вчерашний день;
2) полученные на предыдущем шаге данные очищяются;
3) генерация признаков: формирование финальных датасетов для соотв. моделей и расчет признаков для конкретных сервисов (динамическая цена, прогноз спроса, fraud). Результаты сохраняются в Feature Store.
4) запустить дообучение моделей на новых данных;
5) сравнение метрик новой модели с текущей рабочей моделью на тестовой выборке;
6) если модель прошла валидацию, то деплоем в соотв. сервисы на prod, иначе -- шлем оповещение инженерам о проблеме;

### Замечание к диаграмме C4

Для экономии места приведены только 2 сервиса Booking и Driver, все остальные типа fraud, geolocation, ценооборазование и платежи не преведены, но они также участвуют в этой схеме. Т.е. через механизм CDC базы данные соотв. тенантов отправляют изменения в соотв. топики Кафки. Скорее всего, на каждый сервис, т.е. бд, будет свой модуль CDC, а не один на всех.
