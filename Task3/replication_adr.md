# ADR-qqq: Стратегия глобальной репликации данных для макрорегионов ЮВА и ЛА

## Контекст

Проектируем глобальную high-load платформу заказа такси. Система развернута в четырех регионах : ЮВА: Сингапур , Джакарта . ЛА: Сан-Паулу, Мексика.

## Ключевые бизнес-требования:

- **Доступность 99.99%**. Максимальный простой — до 52 минут в год;
- **Низкая задержка.** Сетевой отклик для пользователей < 50 мс;
- **Комплаенс.** Соответствие законам LGPD (Бразилия) и PDP Act (Индонезия);
- **Сетевые ограничения.** Пинг между Азией и ЛА превышает 300 мс.

## Рассматриваемые альтернативы

### Альтернатива 1: Единая глобальная БД (Master-Slave)
Один регион является главным для записи. Остальные только читают.

- **Минусы**: Запись из Бразилии в Сингапур занимает >300 мс. Высокий риск потери данных (RPO) при падении Master-региона.

### Альтернатива 2: Полностью изолированные регионы (shared nothing)

Каждый регион работает как суверенный остров. Данные не связаны.

- **Минусы**: Невозможен глобальный роуминг пользователей. Сложно собирать общую бизнес-аналитику.

### Альтернатива 3: Гибридная Active-Active архитектураСинхронный консенсус внутри макрорегионов. Асинхронная изоляция между континентами.

Синхронный консенсус внутри макрорегионов. Асинхронная изоляция между континентами.

## Решение

Выбрана "Альтернатива 3". Стратегия разделена по трем инфраструктурным слоям:

1. Транзакционный слой (База данных заказов — CockroachDB)
   - Географическое шардирование на уровне строк по признаку location_id;
   - Внутри макрорегионов: включить синхронную репликацию на основе кворума (Raft). Задержка записи составляет десятки мс;
   - Между континентами: полностью отключить синхронную репликацию заказов;
2. Слой глобальных справочников (Профили пользователей)
   - Таблицы учетных записей реплицируются между континентами асинхронно. Это обеспечивает роуминг клиентов без задержек при заказе. Т.е. копируется только уникальный id пользователя и его пароль.
3. Слой асинхронных событий (Шина Kafka)
   - Развернуть изолированные кластеры Kafka в каждом регионе;
   - Использовать Kafka MirrorMaker 2 для зеркалирования топиков саги bookings и payments только внутри макрорегионов.

## Обоснование

- Обеспечение отказоустойчивости . При отказе Сан-Паулу трафик перенаправляется в Чили. Благодаря кворуму, база данных в Чили уже содержит 100% актуальных транзакций.
- Высокая производительность. Локализация записи удерживает задержку транзакций в пределах 30–40 мс.
- Выполнение законов (Data Residency). Персональные данные бразильцев физически остаются в ЛА. Данные индонезийцев остаются в Азии.
  

## Последствия выбранного решения

### Положительные (Pros):

- Высочайшая катастрофоустойчивость системы.
- Минимальный сетевой пинг для пользователей.
- Юридическая чисто перед локальными регуляторами(комплаенс).

### Отрицательные 

- Сложность разработки. Необходима поддержка парадигмы Eventual Consistency для профилей пользователей при роуминге. 
- Стоимость инфраструктуры. Поддержка 4-х раздельных кластеров Kafka, Redis и СУБД существенно увеличивает затраты.


## Замечания и ограничения

Пару слов об ограничениях -- надо понимать, что если мы потеряли весь ЮВА кластер, то пользователи в ЮВА не смогут вызвать такси. Репликации в данном случае нужна, чтобы не потерять бизнес данные пользователей при аварии, а не делать сервис  24/7/365.  А вот если мы потеряли сервер в Сингапуре, то за счет пространственной близости и небольшого пинга до Джакарты, сервис в Сингапуре по прежнему может быть доступен в полном объеме, телеметрия от такси вполне может собираться и через Джакарту, например. Будет работать чуточку медленнее, но работать будет и такси можно будет заказать. Т.е. глобально мы реплицируем только данные, а в региональных кластерах добавляется еще отказоустойчивость. Ну и CAP теорему никто не отменял -- при глобальном сбое система в лучшем случае будет доступна для чтения.
